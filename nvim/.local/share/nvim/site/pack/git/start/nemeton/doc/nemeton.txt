1. INTRODUCTION                                         *nemeton-introduction*
                                                                     *nemeton*

Nemeton reviews GitLab merge requests in ordinary buffers. It checks the
branch out, fetches every discussion on the merge request, and marks the
lines that carry one in the gutter of whatever file you open. You read
the code as code -- with your LSP, your treesitter, your keys -- and the
conversation is drawn on top of it.

It talks to GitLab through the `glab` command line client. There is no
HTTP client in here and no token in a config file: every call is a
`glab` subprocess, and `glab` already knows how to authenticate.

What it does:

  - lists the open merge requests of the project this repository points
    at, as a table you can read -- number, CI, size, author, staleness,
    conversation -- with the commits of the row under the cursor, or
    what it says it is for, in a pane under the list;
  - opens one: `glab mr checkout`, then every discussion on it;
  - marks the lines carrying a thread, in every file you open, for as
    long as the review is on;
  - shows a thread in a float, and one at a time in a pane beside the
    code that reads whatever `]m` walks to and answers it from there;
  - writes new threads, replies, suggestions and overall comments, and
    keeps them unsent until you publish the review as a whole;
  - resolves and reopens threads, approves the merge request, and says
    what CI did, job by job.

2. REQUIREMENTS                                         *nemeton-requirements*

  - Neovim 0.10 or newer. `vim.system()`, `vim.ui.open()` and the
    extmark fields this draws with are all 0.10, and none of them
    degrade: on anything older nemeton says so and does nothing.
  - `git`, and a repository with a GitLab remote.
  - `glab` -- https://gitlab.com/gitlab-org/cli -- authenticated, or a
    token nemeton can reach. See |nemeton-credentials|.
  - GitLab 15.10 or newer to keep a comment unsent (the draft notes
    API). Everything else works on anything current; an older GitLab
    loses the unsent comments and keeps the rest.
  - A Nerd Font, or new glyphs. See `comments.sign_open` and its
    neighbours in |nemeton-config-comments|.

`:checkhealth nemeton` answers all of this. See |nemeton-health|.

3. GETTING STARTED                                   *nemeton-getting-started*

>
    glab auth login          " nemeton does nothing without a token
    cd <a repository with a GitLab remote>
    nvim
    :Nemeton                 " the list; <CR> checks one out
<
Calling `setup()` is optional. The command and the one global key are
registered when Neovim starts and load nothing until they are used; the
first of them to be used wires up the rest. Call it to pass a table in:
>
    require("nemeton").setup({
      glab = {
        host = "gitlab.example.com",
        token = function()
          return vim.trim(vim.fn.system("pass show gitlab/token"))
        end,
      },
    })
<
Every key of |nemeton-configuration| can go in there, in the same shape.

A review, end to end:

  1. `<leader>ml` -- the list. `c` shows the commits of the row under
     the cursor, `d` what it says it is for.
  2. `<CR>` -- check that one out and fetch its threads. The window
     stays up, saying what it is doing, until the review is loaded.
  3. Read the code. Threads are marked in the gutter; `]m` and `[m`
     walk them, `<leader>mp` peeks at one, `<leader>mx` opens the pane
     beside the code and reads them there -- and answers them, where
     `r`, `x`, `e` and `d` are reply, resolve, edit and delete.
  4. `<leader>ma` on a line -- write a comment. `:w` keeps it for the
     review. Over a visual selection it comments on all of it;
     `<leader>ms` there suggests a change instead.
  5. `<leader>md` -- the merge request itself: CI, approvals, size,
     how much conversation. `a` approves it from there.
  6. `<leader>md` then `s` -- send everything you kept, as one review.

4. COMMANDS                                                 *nemeton-commands*

                                                                    *:Nemeton*
:Nemeton                Open the merge request list. |nemeton-list-window|

:Nemeton list           The same thing, spelled out.

:Nemeton open {iid}     Check merge request {iid} out with `glab mr
                        checkout` and load its threads.

                        Without {iid} it asks for one, completing over
                        what is open -- by number and by title, since
                        the reviewer at this prompt knows it as "the
                        proxy one" and the number is the thing they
                        would have to go and look up. The number is
                        taken off the front of the answer, so a
                        candidate accepted whole, a bare `42` and a
                        pasted `!42` are one answer. `keys.global.open`
                        puts it on a key; it is unbound by default,
                        because the queue is the way in nine times out
                        of ten.

:Nemeton close          End the review: the markers and the review keys
                        go away. The branch stays checked out.
                        `<leader>mq` is the same thing from the buffer.

:Nemeton comments       Markers on or off. A redraw, not a refetch.

:Nemeton expand         The conversations themselves: one at a time in
                        a pane beside the code, on the side
                        `comments.expand` says. Again to fold them back
                        to gutter markers. |nemeton-pane-window|

:Nemeton peek           The thread under the cursor, in a float that
                        closes on the next cursor movement.

:Nemeton description    The merge request's own window: what it is for,
                        what CI made of it, who has approved it, how
                        much conversation is on it -- and the keys to
                        act on all three. |nemeton-detail-window|

:Nemeton comment        A new thread on the line under the cursor.

:Nemeton reply          A reply into the thread under the cursor.

:Nemeton edit           Rewrite one of your comments in the thread under
                        the cursor.

:Nemeton delete         Delete one, after asking.

:Nemeton resolve        Resolve the thread under the cursor, or reopen
                        it if it is already resolved.

:Nemeton suggest        Suggest a change to the line under the cursor,
                        or to the lines of the last visual selection.
                        The composer opens with the current text in a
                        `suggestion` fence, in the colours of the
                        language it is written in |nemeton-syntax|;
                        what you leave in it is what the author can
                        apply with one click.

:Nemeton link           Put a link to the line under the cursor -- or to
                        the lines of the last visual selection -- on the
                        clipboard, as a permalink against the merge
                        request's head sha. What you paste into a
                        comment to point at code the comment is not
                        about; drawn as `src/app.lua:42` wherever
                        nemeton reads one back |nemeton-markdown|.

:Nemeton create         A window for a merge request of your own, for
                        the branch you are on: the title, whether it is
                        a draft, the description, the branch it goes to
                        and the labels -- with what CI made of the
                        branch and how much it changes underneath.
                        |nemeton-create-window|

:Nemeton note           A comment on the merge request rather than on a
                        line of it.

:Nemeton notes          Every comment on the merge request, one line
                        each, in a window that reads and answers them.
                        |nemeton-notes-window|

:Nemeton threads        Every thread on the merge request, into the
                        |quickfix| list.

:Nemeton conversation   The same threads, to read rather than to walk.
                        |nemeton-conversation-window|

:Nemeton jobs           What CI did, job by job. |nemeton-jobs-window|

:Nemeton publish        Send every comment you have kept unsent, as one
                        review.

:Nemeton approve        Approve the open merge request.

:Nemeton unapprove      Take the approval back.

:Nemeton refresh        Refetch the discussions. The forge is the source
                        of truth; this is how you pick up what somebody
                        else said while you were reading.

:Nemeton status         Which merge request is open, and how much is on
                        it.

:Nemeton token          Type a token in for this editor session.
                        |nemeton-credentials|

:Nemeton forget-token   Drop it again.

5. MAPPINGS                                                 *nemeton-mappings*

Every key here is `config.keys.*` and every one of them can be set to
`false` to unbind it. See |nemeton-config-keys|.

ALWAYS                                               *nemeton-mappings-global*

    <leader>ml      the merge request list
                    ...and `keys.global.open`, unbound, for the number
                    asked for instead |:Nemeton|

THE REVIEW                                          *nemeton-mappings-session*

Bound while a merge request is open and taken away again by `:Nemeton
close`. An editor with no review on is an editor where `]m` means what
it has always meant.

Everywhere, and not only on the files of the repository. `]m` means "the
next thing owed an answer", and the thing it walks to is in whichever
file it is in: the question is asked as often from the quickfix list the
threads were read in, from the terminal the tests ran in, from the
commit message being written, or from a file of another project, as it
is from the code itself. The verbs that *are* about the line under the
cursor are out there too, and say what they always say when there is no
line to be about -- this buffer is not a file of the repository, or
there is no thread here.

Bound twice over, in fact: globally, and again on every file of the
repository whenever something else has had a turn at the buffer. A
global mapping is the weakest kind there is, and a filetype plugin maps
into the buffer it is loaded for -- Neovim's own ftplugin/python.vim
takes `]m` and `[m` for its method motions. Only a buffer-local mapping
wins that, and the file is loaded again every time it is re-read, which
a checkout makes it do.

    <leader>mx      expand the conversations -- the pane beside the code
    <leader>mp      peek at the thread on this line
    <leader>ma      comment on this line, or (visual) on these lines
    <leader>ms      (visual) suggest a change to these lines
    <leader>mL      a link to this line, or (visual) to these lines
    <leader>md      the merge request's own window -- the one review key
                    that is not about the line under the cursor
    <leader>mq      end the review -- the markers and these keys go
                    away, and the branch stays checked out
    ]m  [m          next / previous thread, across the whole merge
                    request -- not just this file

What is bound out here is what the pane cannot do: read the review, walk
it, and start a comment where the cursor is. Acting on a conversation
that is already there -- answering it, settling it, rewriting or
deleting a comment in it -- happens in the pane |nemeton-pane-window|,
where the thread is on the screen and the cursor can be put on the
comment being talked about.

They were four keys out here, and each of them asked a question the pane
answers by being open: which thread on this line, and which comment in
it. Answering out of a picker what you could have answered by putting
the cursor on it is the long way round.

So the rest are `false` in `config.keys.session` and live where the
question they answer is asked -- in the pane, one letter further in on
`<leader>md` (|nemeton-detail-window|), or as a `:Nemeton` verb typed
once in a review:

    reply = false       `r` in the pane
    resolve = false     `x` there
    edit = false        `e` there
    delete = false      `d` there
    notes = false       `c` on <leader>md -- every comment on it
    approve = false     `a` there
    jobs = false        `p` there
    publish = false     `s` there
    threads = false     |:Nemeton| `threads`
    toggle = false      |:Nemeton| `comments`

Give any of them a string to have it out here as well; nothing else has
to change, and every one of them is a |:Nemeton| verb either way.

6. WINDOWS                                                   *nemeton-windows*

Every window here is a float with its keys written across the top of
it, save the pane, which is a split because it is read *beside* the code
rather than over it.
None of them takes over `hjkl`, `/` or anything else you read with. The
key that closes one puts the cursor back in the window it was pressed
in, rather than wherever Neovim would have left it -- which on a split
screen is the top left window and not where you were reading. The keys
that close a window on the way somewhere -- to the code a thread is
about, to the composer -- go there instead.

THE LIST                                                 *nemeton-list-window*

A queue with nothing in it still carries the keys across the top: what
to do about "no opened merge requests" -- look at the merged ones, or
write one of your own -- is the one thing a reader cannot guess from an
empty window.

One row per merge request: number, CI, how far its approvals have got,
title, how much it changes, who wrote it, how stale it is, how many
comments -- and, at the end of the row in the colour an unsent comment
is drawn in everywhere else, how many of them are yours and still
unsent.

The approvals are the tick and the count -- `✓2/2`, `◌0/1` -- in the
two colours the merge request's own window says them in, and nothing at
all where nobody is required and nobody has been in: that is a merge
request nothing is waiting on rather than one short of an approval, and
a dim zero would say the opposite. Who has approved it is a name, and
names are `<leader>md` or the pane under the list.

CI, the approvals and the size are asked for only where they are still
a question -- an open merge request. On one that is merged or closed
they are history, the three columns are empty, and the queue is drawn
without asking the forge anything.

    <CR>            check this one out and load its threads
    c               the commits of the row under the cursor
    d               what it says it is for
    p               what CI made of it, job by job
    s               opened / merged / closed / all, round and round
    ]               another page of them, under the ones on the screen
    +               open one of your own, for the branch you are on
    r               refetch
    o               open it on GitLab
    q               close

The window is up before the answer is: it opens on the keypress saying
that it is fetching, fills in when the queue lands, and each row's CI,
approvals and size arrive afterwards and are drawn where the row
stands. `<CR>`
does not close it either -- it says which merge request it is opening
and stays up until the review is loaded, so a slow checkout looks like a
slow checkout rather than like nothing at all.

One page at a time, and `]` for the next one under it -- the queue is
appended to rather than replaced, and the cursor goes to the first row
that is new. A queue of what is open is a page long; a queue of what is
merged is a history, and what is being looked for in a history is
usually further down than thirty rows. The key stops being offered when
a page comes back short, which is the only way to know there is no
next one: GitLab counts them in a header `glab` does not pass on.

A checkout that fails -- the working tree has changes in it, the branch
is checked out in another worktree -- says so in the window, folded to
fit and whole: what git said was in the way and what to do about it,
and what `glab` concluded from that, without the fetch report, the
banner between them, or an "exit status 1" that says only that
something failed. `<CR>` puts the queue back underneath it without
asking the forge for it again. What `glab` said in full is in the log.
|nemeton-log|

`s` walks the queue through the four states GitLab has: the open ones a
review queue is made of, then the merged, the closed, and all of them
together. The window's title says which of the four is on the screen and
every row says it for itself -- `merged` in the colour of a thing that
is through, `closed` in the dim one -- because "all" is one press away
and a mixed queue is read a row at a time. It is a question asked, not a
setting changed: close the window and the next one opens on
`list.state` again. |nemeton-config-list|

`c`, `d` and `p` open a pane under the list for the row the cursor is
on, and follow the cursor down the queue. `d` shows exactly what the
merge request's own window shows.

`p` is the CI column asked what it means: the jobs of the head
pipeline, grouped under their stages with what each one did and how
long it took -- the same table |nemeton-jobs-window| draws, on the same
key the merge request's own window puts the pipeline on. "failed" in a
column is where the question starts, and "which job" is a question
about a merge request nobody has opened yet: often it is the answer to
whether to open it at all. A merge request with no pipeline says so.
What comes back is kept until `r`, like the rest of the pane -- a
pipeline that was running when you looked is refetched by the key that
refetches the queue.

The list does not move when the pane opens: its top edge stays where it
is and the pane takes the room below. Where there is not enough of it
the list gives up rows from the bottom, and only when it has none left
to give does the pair come up the screen. `list.preview_height` is the
most the pane will take. |nemeton-config-list|

THE MERGE REQUEST                                      *nemeton-detail-window*

`<leader>md`, or `:Nemeton description`. What it is for, and the state
it is in: CI, approvals, how big the change is, how much conversation
there is and how much of it is yours and unsent.

    a               approve it, or take the approval back
    s               send every comment kept unsent
    c               every comment on it, one line each
    p               what CI did, job by job
    o               open it on GitLab
    r               refetch the approvals and the diff
    q               close

The threads that are on the code are not here: they are read where the
code is -- in the gutter, on `]m`, in the quickfix list.

THE COMMENTS                                            *nemeton-notes-window*

`:Nemeton notes`, or `c` from the window above. Every conversation on
the merge request, in one place: the ones on code, by file and line,
then the ones that are about no line at all.

    <CR>            go to the code this comment is about
    r               reply to it
    a               write a comment on the merge request
    t               write one people can reply to
    e               edit one of its comments
    d               delete one, after asking
    <C-]>           follow what is under the cursor |nemeton-follow|
    R               refetch
    q               close

The same keys as the every-thread window below, because it is the same
threads read at a different depth. `<CR>` on a comment that is about no
line -- one on the merge request itself -- says so and leaves the window
where it is, rather than closing it to go nowhere.

An index rather than a transcript. Each thread is its opening note and
nothing else, on two lines: who wrote it and when, and what they said.
The first line carries what a list has to say and a block does not --
where the thread sits, as `path:line`, for the ones that sit anywhere;
`✓ resolved` when the argument is over; `unsent` when it is yours and
has not gone; and `+2` for the answers under it that are not on the
screen. |:Nemeton| `conversation` is where those are read.

GitLab will not take a reply to a comment that was posted on its own;
nemeton says so rather than failing the post, and `t` is how you start
one that can be answered.

EVERY THREAD                                     *nemeton-conversation-window*

`:Nemeton conversation`. All of it, to read rather than to walk.

    <CR>            go to the code this thread is about
    r               reply
    e               edit the comment under the cursor
    d               delete it, after asking
    <C-]>           follow what is under the cursor |nemeton-follow|
    R               refetch
    q               close

THE PANE                                                 *nemeton-pane-window*

`<leader>mx`, where `comments.expand` is "right" or "bottom". One
conversation in a window beside the code rather than in it, named by
file and line across the top.

One at a time, because the pane is where a thread is read, and a window
holding every thread in the file is a window to navigate before anything
in it can be read. `]m` and `[m` are the navigation -- they are the walk
through what the review is owed anyway -- and they are the only thing
that changes what is in there. `<CR>` on a thread in the every-thread
window, the comments window or the quickfix list puts that one in it.

Not the cursor. Reading a comment and reading the code it is about are
the same activity: you go to the line it names, then to the function
that line calls, then back through three files -- and half of that is
standing on lines other people have commented on too. A pane that
answered the cursor would spend that walk showing everything except the
thing being read. So it holds still, and the comment stays on the screen
while the code under it moves.

One pane, not one per window. It is a place to read, like the quickfix
window, and a screen with a pane against every split is a screen with no
code left on it.

Across the top, on the one line of it that does not scroll: the state of
the conversation in the glyph the gutter marks its line with, where it
sits, how many answers there are and whether the line carries a second
argument -- and `g?`, on the right.

`g?` is the whole of what the header says about the keys, because there
are eleven of them and a header has room to name three. It prints them
in a float, read out of the bindings themselves rather than out of a
list written beside them: a help that is a second copy of the keymaps is
a help that is wrong the first time one of them moves. `q` or `<Esc>`
closes it and puts the cursor back in the pane. All of it fitted to the width of
the window, in the order it can be spared: the keys first, then how much
of it there is, and last the head of the path, which goes as
`…app.lua:3` because the end of a path is the half that names the file.
The heads inside the block are trimmed the same way -- the commit, then
the date, and the name of who said it only when dropping both was not
enough.

    <CR>            go to the code this thread is about
    r               reply
    e               edit the comment under the cursor
    d               delete it, after asking
    x               resolve the thread, or reopen it
    <C-]>           follow what is under the cursor |nemeton-follow|
    +               react to the comment under the cursor
    R               refetch
    q               fold the conversations away
    ]m  [m          the next thread owed an answer, and the previous
    g?              all of the above, in a float

`e` and `d` act on the comment the cursor is standing on rather than on
one picked out of a list: the whole conversation is drawn in here, so
the reader is already pointing at the one they mean. The head of a note
counts as part of it. On a line that is nobody's comment -- the blank
between two threads, the code one was written against -- the list is
still asked.

`x` is the one verb here that is about the thread rather than a comment
in it: an argument is settled as a whole.

`+` reacts |nemeton-reactions|, and reacting again with the same emoji
takes it back -- which is GitLab's own gesture and the only one there
is. It is `+` and not a letter for the same reason `+` is `+` in the
queue: nothing in this window is a motion, and the one key here that
adds something without opening a window to write it in should not look
like the letters that read.

`]m` and `[m` in here move the cursor of the window the pane was opened
from -- the walk happens in the code, and your reading position stays
in the prose.

`q` is `<leader>mx` from inside: while the pane is open it is what
"expanded" means, so closing it folds the conversations away rather than
leaving the session saying they are open. Closing the window any other
way says the same thing.

                                                          *nemeton-reading*

While a conversation is on the screen in there, the code says which
lines it is about -- in the gutter, and under them.

The gutter first. The bubble marks the line a thread is anchored to; a
comment written over a selection is about the lines above that too, and
with the words in a window next door nothing else says so. Those lines
carry `comments.sign_span` -- the rail the thread carries down its left
in the pane -- in the colour of the same state, and under the bubble's
own priority, so a sign column one cell wide still draws the bubble and
a wider one draws both.

...and a band under the whole of it |hl-NemetonReading|, which is what
the gutter alone could not say. Every line carrying a thread has the
same bubble on it, so with three conversations in a file nothing out
here says which of them is the one you are reading. The rail says where
a block starts -- but only where there is a block, and a comment about
a single line has no lines above it to put a rail on, and on the anchor
line the bubble is drawn instead. The band says it in all three cases,
and it says it with a sign column that is off. `comments.reading_ground
= false` leaves the gutter to do what it can.

THE PIPELINE                                             *nemeton-jobs-window*

`p` on the window above, or `:Nemeton jobs`. Every job of the head
pipeline, its stage, its status and how long it took.

    <CR>            what the job under the cursor printed
    o               open the job under the cursor on GitLab
    r               refetch
    q               close

A JOB'S LOG                                               *nemeton-log-window*

`<CR>` above. What that job printed, in a tab of its own -- not a float
like everything else here: a build log is thousands of lines read by
searching them, and it is the one thing this plugin shows that you want
open while you go back to the code it is complaining about. The cursor
starts at the end, where a failure is.

    R               refetch -- a running job has more of it every second
    o               open the job on GitLab
    q               close the tab

The jobs window is left standing in the tab it was opened from, so `q`
puts you back in front of it. What the runner wrote for a terminal is
taken out on the way in: the colour escapes, GitLab's `section_start:`
markers, and the carriage returns a progress bar was drawn with -- of
which only what the line ended up saying is kept.

A MERGE REQUEST OF YOUR OWN                            *nemeton-create-window*

`+` in the list, or `:Nemeton create`. Everything `glab mr create`
would ask at a prompt, on one screen and in any order:

    title           what it is called
    draft           whether anybody is being asked to review it yet
    target          the branch it goes into
    labels          the ones the project has
    description     what it is for

The cursor sits on a field and `<CR>` changes it: the title in a
prompt, the description in the composer (|nemeton-writing|), the target
branch and the labels picked from what the project has. The labels are
a dropdown that comes back with the tick moved until it is dismissed --
labels come in threes, the team, the area and the release, and pressing
the key three times to say so is three times as long a way of saying
it. A project the forge will not list the labels of falls back to
typing them, and says which of "there are none" and "it would not say"
happened. However the
composer is left -- its own keys, or `:q` like any other split -- the
cursor comes back here. A title that
begins `Draft:` sets the switch instead of staying in the title --
GitLab reads the prefix off the title itself, so the two make the same
merge request, and only one of them leaves the title as the thing that
was typed.

Under the fields are the three facts nobody types: what CI last made of
the branch -- it has no pipeline of its own yet, and the branch has run
one against the same commits -- and how many files and lines it
changes, in the colours the queue counts a merge request in, because it
is the same fact about the same branch. The count is git's,
`<target>...HEAD` against `origin/<target>` where that is here and
`<target>` where it is not, because the merge request whose diff GitLab
would answer with does not exist yet.

    <CR>            change the field under the cursor
    <C-s>           open the merge request
    r               ask CI and git again
    X               throw away what has been typed
    q               close it

`q` keeps everything. The window is per branch and lasts as long as the
editor session: press `+` again and the title, the description and the
rest are where you left them. A merge request is written between two
interruptions like anything else. What has gone out is forgotten -- the
next `+` on that branch is a new merge request.

The branch is pushed on the way out (`--push`) and nothing is confirmed
at a prompt (`--yes`): a subprocess with no terminal is not a place to
be asked anything.

What the forge answers with is the merge request that was made, so that
is what opens: the queue it was written from closes -- it was a list of
what there is to review, and what there is to review now is this -- and
the review starts on the new one, discussions and all.

THE PEEK FLOAT                                           *nemeton-peek-window*

`<leader>mp`. The thread on this line, over the code, gone on the next
cursor movement. For reading; the keys that answer it are the review's
own, |nemeton-mappings-session|.

==============================================================================
7. WRITING A COMMENT                                         *nemeton-writing*

`<leader>ma` opens a small split. What you write in it goes to GitLab
anchored to the line the cursor was on, with the position the API wants:
the three diff shas, the path on both sides, and the line.

Pressed over a visual selection it comments on the whole of it. GitLab
anchors such a thread to the *last* line of the span and carries the
rest as a line range, which is how it draws "Comment on lines 57 to 59"
and how nemeton knows to underline all three when the thread comes back.
`<leader>ms` there suggests a change to those lines instead. Every line
of the selection has to be a line the merge request touches: a range
that reaches outside the diff is refused before the split opens, the
same way a single line outside it is.

On GITLAB OLDER THAN 18.6 the range goes without its two line numbers.
Up to 18.5 the API declares them as strings, coerces the integers a
client sends into them, and then validates the position it built against
its own schema, which says integers -- so it refuses its own payload
with `position: ["must be a valid json schema"]` and nothing about which
field. nemeton asks the forge what it is before it sends the first one,
and leaves those two out where they will not be taken: the line codes
are what anchor the comment, and what is lost is GitLab's own "Comment
on lines 57 to 59" label, which it reads from the numbers. A forge that
will not say what it is gets the whole payload, and is sent it again
without them if it refuses -- once, and remembered for the session, so a
patched instance costs one refused POST and no more. `$XDG_STATE_HOME`
|nemeton-log| records when that happens.

                                                            *nemeton-old-side*
A LINE THE CHANGE DELETED is in no buffer of the branch -- that is what
deleted means -- so there is nowhere to put a cursor and press
`<leader>ma`. nemeton does not draw a second copy of your file to fix
that: reviewing in the buffer you are editing, with your own edits and
your own LSP in it, is the whole shape of the plugin, and a rendering of
the same file beside it is the thing it exists not to be.

What it does instead is take an old side from whoever drew one. Any
buffer showing the file at the revision the merge request is measured
against will do, and there are three ways of saying which:

    comments.old_side   a function of yours, given a buffer number and
                        returning `{ path = ..., sha = ... }` or nil
    b:nemeton_old       the same table, on the buffer itself
    the buffer's name   `<scheme>://…/<sha>/<path>`, which is how
                        fugitive, diffview and gitsigns each name one

The first two are told and are believed. The last is a guess and has to
prove itself: it is taken only when the sha is one this merge request is
compared with, so an ordinary file under a directory named like a sha is
not mistaken for a revision of something.

That check applies to all three. A buffer showing some *other* revision
-- one commit's parent, a stash, a tag -- would build a position against
a diff GitLab has never seen, and a comment anchored to one of those
either bounces or lands where nobody meant; so it is refused, and the
message says what the buffer is showing instead.

In such a buffer the review keys mean what they say on the old file. A
line the change removed is anchored on the old side and nowhere else; a
line it left alone is anchored on both, because it is the same line and
the thread belongs where the reader of the branch will find it.
`<leader>ms` is refused there -- a suggestion is a patch the author
applies to the branch, and there is nothing on the old side to patch --
and `<leader>mL` links to the line at that revision rather than at the
head.

Wiring up a diff view -- the example is uatis, which puts the old
revision in a window of its own: >lua

    require("nemeton").setup({
      comments = {
        old_side = function(bufnr)
          local view = require("uatis.oldside").view_for(bufnr)
          if view then
            return { path = view.old_path or view.relpath, sha = view.rev }
          end
        end,
      },
    })
<
Neither plugin has to have heard of the other. The function lives in
your config, which is the only place that knows you run both, and it is
asked when a key is pressed rather than watched for -- so nothing has to
fire an event, and nothing goes stale when the view redraws.

    <C-s>  or  :w   keep it for the review (send it, on a reply)
    <C-p>           post it to the merge request now (keep it, on a
                    reply)
    <C-b>           a suggestion block over the lines this is about
    <C-x><C-o>      the people you can put an `@` in front of
    q               close it; what is in it is here again next time

`q` PUTS IT AWAY RATHER THAN THROWING IT AWAY. Closing the composer with
something in it keeps that something, and the next time the same comment
is written -- the same lines of the same merge request, the same thread
answered -- it comes back. Across restarts, too, which is the point of
it: `nvim` gets restarted between reading a merge request and finishing
the sentence about it more often than anybody would like, and a review
comment is prose that vanishing means writing twice.

What is remembered is what is in the buffer, which is how one is thrown
away on purpose: empty it and close it. It is forgotten three ways --
sent or kept on the forge, closed with nothing in it, or
`compose.remember_days` old (30 by default, because anything past that
is a comment you walked away from a month ago). They live in
`$XDG_STATE_HOME/nemeton/composing.json`, beside the log, at 0600.

This is the one thing here that writes what you typed to disk, and
`compose.remember = false` is that off. Nothing else is written down:
see |nemeton-credentials| for the token, which never is, and
|nemeton-drafts| for a comment kept for the review, which lives on the
forge and is therefore still there on another machine.

`<C-b>` is there because a comment turns into a suggestion halfway
through writing it: you get as far as "it should be" and notice that
showing it is shorter than saying it. It drops GitLab's fence in under
what you have written, with the lines the comment is about already in
it, and leaves the cursor on the first of them -- a suggestion is an
edit of what is there, and retyping four lines to change one word is
how a reviewer decides not to suggest anything. Bound only where there
are lines to put in the block: not on a comment about the merge request
as a whole, and not on the old side of the diff, where a suggestion is
a patch of code the branch does not have. `:Nemeton suggest` is the
same block from the other end, where the whole comment is one.

MENTIONS                                                    *nemeton-mentions*

`@` and the first letters of a name: the menu comes up on its own, and
`<C-x><C-o>` asks for it where it does not. What goes in is `@username`,
sigil and all, because that is what GitLab turns into a notification --
and the names are the members of this project and of the groups above
it, which is who GitLab will accept. See |nemeton-config-compose| for
the two switches and for what to point a completion engine at.

EMOJI                                                          *nemeton-emoji*

`:` and the first letters of a shortcode completes the same way, through
the same one `omnifunc`: which of the two is being typed is the sigil in
front of the cursor. What goes in is `:tada:`, both colons and all,
because that is what GitLab draws as a picture -- and the menu carries
the picture beside the name, since nobody remembers which of `tada` and
`confetti_ball` is which. A name is offered for what it contains as well
as for what it starts with: `:check` is reached for by somebody who
wants `white_check_mark`.

Read back, a `:name:` is drawn as the character (`comments.emoji`) --
the way the forge drew it on the page the comment was written on. Drawn
only: what is sent when a comment is written or rewritten is the text
its author typed, colons and all. A suggestion is left alone too; it is
code, and code that says `:tada:` says `:tada:`.

The names are in `lua/nemeton/emoji.lua`, and they are what a review is
written with rather than the whole of gemoji. One that is not there is
left exactly as it was typed, which is what a forge does with a name it
does not know either.

                                                          *nemeton-reactions*
REACTIONS are the other half of that: the emoji people put *on* a
comment rather than in one. Drawn under the note they were given to, a
picture per emoji with a count beside it, gathered by name and in the
order they were first given -- which is what the page the comment was
written on shows. Three thumbs on a suggestion is an argument being
over, and nobody writes "agreed" three times.

`+` in the pane gives one, and gives it to the comment the cursor is
standing on. Picking an emoji you have already given takes it back --
GitLab's own gesture, and the only one there is -- so yours are drawn
in a colour of their own |hl-NemetonReactionMine| and the picker says
which they are. `comments.reaction_names` is what it offers, and
anything already on the note is offered too, so a reaction somebody
left from the web page is one you can join.

The names of the people who gave them are not drawn. That is a hover on
the web page and a line of usernames in here, and a review is read for
what people wrote.

All of it is one GraphQL call beside the discussions on every refresh.
REST publishes reactions one note at a time, so the REST answer to
"what has been reacted to in this review" is a request per comment --
forty subprocesses to draw a row of thumbs. It fails quietly: an
instance too old for the field, a token without `read_api`, GraphQL
turned off, all of them are a review drawn without pictures rather than
an error after every post. `comments.reactions = false` is that on
purpose, and one call fewer.

                                                              *nemeton-drafts*
KEEPING IS THE DEFAULT. A comment you write becomes a GitLab draft note:
it is drawn on its line in its own colour, with a pencil in the gutter,
and it goes nowhere until `s` on `<leader>md` (`:Nemeton publish`) sends
every one of them at once. That is what submitting a review is -- and a
comment posted the moment it is typed is a comment you cannot take back
after reading the next file. It sits on that window beside the approval
and beside the count of what is still unsent, which are the two things
you would want to know before pressing it.

`<C-p>` posts on the spot, for when that is what you mean. Swap
`config.keys.compose.keep` and `config.keys.compose.post` to swap the
two round; nothing else knows which is which.

                                                             *nemeton-replies*
A REPLY IS THE OTHER WAY ROUND: `<C-s>` and `:w` send it, `<C-p>` keeps
it for the review. A reply is half of a conversation somebody else is
already in, and one held a publish at a time is not one. GitLab also
files an unsent reply with your other drafts rather than under the note
it answers, so a kept reply is invisible to the person waiting for it
and invisible in the thread as well -- nemeton folds one back into the
thread it belongs to wherever it draws it, marked `unsent`, so that a
reply kept by the other key or written in GitLab's own interface is at
least visible to you.

Draft notes are GitLab 15.10 and newer. On an older instance `<C-s>`
fails and `<C-p>` works.

                                                           *nemeton-refused*
A WRITE THE FORGE REFUSED says what the forge said -- its own words,
taken out of the JSON body glab prints whole, so `position: must be a
valid json schema` rather than the braces around it -- and then asks
the forge again.

The second half is not tidiness. "It failed" and "nothing happened" are
not the same thing: a call can land, be written down, and still come
back an error -- a timeout after the note was created, a proxy that
gave up on the way home, a 4xx about something GitLab did after
creating it. The editor is then holding a picture the forge does not
agree with, and the comment you can see in `glab` is the one that is
not on your screen. Everything that posts refetches when it succeeds
for the same reason; this is that reason applied to the other half, and
it costs one call on a path that is rare.

                                                            *nemeton-markdown*
A COMMENT IS MARKDOWN, and wherever one is read it is drawn as the page
the forge would have drawn rather than as the characters it was typed
with. The composer is the other half of that promise: what is written
there is the source, because the source is what is posted.

A LINK is drawn as the words it was given.
`[the failing job](https://…/-/jobs/1234)` is four words and a hundred
characters of where they point, and the hundred are what wraps a
two-line comment across five. `NemetonLink` is the colour -- underlined,
the way a link has always been -- and where it goes is not lost: `<C-]>`
on it follows it. A picture --
`![alt](src)` -- is drawn as its alt text, since a terminal has nowhere
to put a picture and the alt text is the sentence its author wrote for
exactly this case. `comments.links = false` leaves the brackets.

A HEADING is drawn without the hashes. There is no larger type in a
terminal, so a heading here is a colour and a line of its own -- which
is what says "heading" everywhere else in this plugin -- and the level
it was is a weight rather than a size: `NemetonHeading1` is underlined
and bold, `NemetonHeading2` is bold, `NemetonHeading3` is the colour
alone, and `4` to `6` fall away through italic to the quiet colour, so
that a comment with two levels of heading in it reads as two levels. All
six take their colour from `NemetonHeading`. `comments.headings = false`
leaves them.

EMPHASIS is drawn as emphasis: `**must**` in bold, `*maybe*` and
`_perhaps_` in italic, `***both***` as both, `~~was~~` struck through.
These are the marks a reviewer reaches for to say which word of a
sentence carries it, and read as the asterisks they were typed with they
say it about the punctuation instead. `NemetonBold`, `NemetonItalic` and
`NemetonStrike` carry no colour of their own -- a bold word in a settled
thread is dim and bold, and a bold link is still blue and underlined.
An underscore inside a word emphasises nothing, so `snake_case_name` is
a name; a marker nobody closed is the character it is, so `2 * 3` is
arithmetic; and one with a backslash in front of it is the character it
escapes, which is how an asterisk is written in a sentence about a glob.

A LINE THAT ENDS IN A BACKSLASH is markdown's hard break -- "and the
next line goes under this one" -- which is what these windows do with
every line of a comment anyway, so the backslash itself is not drawn.
Only where there is a line under it to break to: one at the end of a
paragraph broke nothing and is a backslash its author typed, and two of
them are an escaped backslash rather than a break.

A CODE SPAN is drawn without its backticks, in `NemetonCode`, and
nothing inside one is markup: `a_b` in backticks is an identifier, a URL
in them is a string somebody quoted rather than a page to go to, and
`@alice` in them is not somebody to notify. A run of backticks closes on
a run of the same length. `comments.styles = false` leaves every marker
as it was typed.

A LINK TO ANOTHER COMMENT -- the `…#note_1234` permalink GitLab's own
"copy link" gives you -- is drawn as `!7 (comment 1234)`, which is what
the forge calls the review and the comment in it, and |nemeton-follow|
on it goes to that conversation rather than copying a URL. The same
argument as a commit permalink: a hundred characters of which twelve are
the content. Words of the author's own win, as ever:
`[why we dropped it](…#note_1234)` is drawn as "why we dropped it" and
still goes there. `comments.links = false` leaves it whole, which also
leaves nothing for the key to find.

A TABLE is ruled and its columns are lined up, with the alignments its
delimiter row asked for. Markdown's own is a table only in the sense
that the columns are named: the cells line up in the source when its
author lined them up by hand, and what is being read here is somebody
else's hand. Too wide for the window, the columns give up room from the
widest first and a cell that still does not fit is cut with an ellipsis
-- a ruled table cannot wrap, because a rule that wraps is two rules.
`comments.tables = false` leaves the pipes.

None of it changes what is sent. |:Nemeton| `edit` posts back the text
its author wrote, brackets and hashes and pipes and all, because that is
what the forge renders and what the next person to edit it has to see.
Inside a fenced block nothing is rendered at all: code that says
`[a](b)` says `[a](b)`.

                                                              *nemeton-follow*
`<C-]>` FOLLOWS WHAT IS UNDER THE CURSOR, in the three windows that draw
a conversation as a real buffer -- the pane |nemeton-pane-window|, the
every-thread window |nemeton-conversation-window| and the comments
window |nemeton-notes-window|. Vim's own key for "go to the thing under
the cursor", doing what it has always done: a tag jump, into a forge
instead of a tags file. On a line with nothing on it to follow it does
nothing and says nothing -- it is pressed while reading.

Five kinds of thing, and one setting each in `comments.follow`:

    mention   @alice                 the person's page on the forge
    commit    a1b2c3d4               the commit's page on the project
    thread    !7 (comment 1234)      the conversation itself, in here
    path      a link written as one  a page on this forge
    url       a link to a page       wherever it points

`true` is the default for all five. For four of them it is the quietest
thing that is still an answer: it says what is under the cursor and puts
the link on the clipboard. Nothing is opened and no window moves -- a
key that took the editor somewhere would be a key pressed once by
accident and then never again -- and what was usually wanted is the
string: the sha to `git show`, the name to ask around about, the URL to
send to somebody.

THREAD is the exception, because it is the one kind whose destination is
not a page somewhere else. A link to another comment on this merge
request is a link to a conversation this editor already has open, so
`true` goes to it: a thread on a line opens its file, puts the cursor on
the line and the conversation in the pane |nemeton-pane-window|, and a
comment on the merge request itself opens the comments window
|nemeton-notes-window| with it under the cursor. The window the link was
read in is left first -- `:edit` from inside a float opens the file in
the float -- so a float closes and the pane stays where it is.

A comment this review cannot show is not silently nothing: a comment on
another merge request, one in a thread resolved while resolved threads
are not drawn |nemeton-config-comments|, or one deleted since somebody
linked it falls back to the clipboard and says which of those it was.

`false` does nothing. A function is yours, and is called with two
arguments -- what is written, and where it points -- and a `thread` with
a third: the thread itself, or nil for one this review has not got
open. >lua

    comments = {
      follow = {
        commit = function(sha)
          vim.cmd("Git show " .. sha)
        end,
        -- a page on the forge in a browser, and somebody else's
        -- website on the clipboard
        path = function(_, href)
          vim.ui.open(href)
        end,
        mention = false,
      },
    }
<
The URL is worked out from the merge request's own page, so a mention
read with no review open has no forge to be a user of: the second
argument is then nil, and `true` says so rather than opening nothing. A
reference GitLab wrote as a path -- `/group/proj/-/issues/3`, which is
what its own autolinks look like -- is resolved against the host, which
is the whole of the difference between `path` and `url`; they are one
kind of thing until you want the forge's own pages opened and nobody
else's.

`url` and `path` were one `link` until they were two. A config that
still says `link` is read as both of them; a config that says `link` and
one of the two new names is a migration half-done, and the specific name
is the one to keep.

`comments.references = false` takes the colours off `@name` and the
shas, and takes them out of what `<C-]>` can find with them: a reference
nobody marked is a reference the key cannot see.

A suggestion is drawn as the diff it is, wherever it is read -- under
the code with |:Nemeton| `expand`, in the peek float, in the every-thread
window: the lines it would replace above it in red, the lines it would
put there below in green. What it would replace is read off the buffer
where the file is open and off the disk where it is not. In the overall
comments there is no line to compare against and the block is drawn on
its own rather than with an invented left-hand side.

                                                        *nemeton-suggest-box*
In a box, and without the fence that made it one. ```suggestion:-1+0 is
not something anybody wrote to be read: it is markup GitLab invented so
that a button on the page can apply the block, and the block underneath
already says everything it says. What the fence did do was mark where
the code started and stopped, and the box says that better -- the two
halves are two bands, and a band with a ragged right edge in the middle
of a paragraph is a stain rather than a block. Every line is padded to
the same width inside a rule.

On the top rule, the two things the fence said that the diff under it
does not: what it is, and `-1 +0` -- how far it reaches, counted from
the line the thread sits on. The red half shows those lines where there
is a file to read them out of; where there is not, the two numbers are
all there is to say how much would be replaced. A box too narrow to name
is still a box, and drops the label.

`comments.suggest_box = false` draws the fence lines again, and the two
halves under them.

                                                              *nemeton-syntax*
The code in it is drawn in the colours of the language the file is in --
on both halves of the diff, and in the composer while it is being
written. A suggestion is the one part of a comment that is not prose,
and in one colour end to end it is the only code on the screen the
editor has not helped you read.

Which half a line is then has to be said some other way, because a
keyword is the colour a keyword is on both of them: each half is drawn
on a band of its own, |hl-NemetonSuggestNew| and |hl-NemetonSuggestOld|,
with the `+` and the `-` in the colour the half used to be.

The band stops at the rules |nemeton-suggest-box|, and is the one band
in a conversation that does. Every other one runs the width of the
editor because there is nothing on its line to say where it ends; here
the box says it, and red running out through a rule and on to the
right-hand side of the window is the colour escaping the thing that was
drawn to hold it. Without the box the band is the whole line again,
which is what it was before there was one.

Not where the line the thread sits on is inside a docstring, a long
string or a block comment. What a suggestion replaces there is prose,
and what this paints is a handful of lines lifted out of a file and
parsed on their own, with nothing around them to say what they are: the
sentences of a docstring parsed as code come back as a keyword here and
a function call there, which is worse than plain -- it is confidently
wrong about what is being read. So the file itself is asked, where the
lines came from and where their context still is, and both halves are
left the colour of the half of the diff they are.

The parser is the one you already have for that language; a file whose
language has none is drawn plainly, and so is everything if
`comments.syntax` is `false`. The block is parsed whole rather than a
line at a time -- a string that opens on one line and closes on the next
is not two lines of anything -- and the `+` and the `-` keep the green
and the red, so which half of the diff a line is stays said.

In the composer this is painted over the top of markdown's own
highlighting: `suggestion` is GitLab's word rather than a language, so
markdown draws the fence as a block of raw text and has nothing to say
about what is in it.

                                                               *nemeton-drift*
WHEN THE CODE HAS MOVED ON. Someone pushes while you are reading, or you
edit the file you are reviewing, and a thread is left sitting on a line
that no longer says what it said. Wherever a conversation is drawn --
in the pane, in the peek float, in the every-thread window -- it then
carries the code it was written against, above the first note, on a
band of its own |hl-NemetonWas|. Nothing is written in front
of it: it is a quotation of the file, the background says so, and a
label saying it again is a word to read before every line. A thread
written across several lines carries all of them, and the band runs the
width of the editor under every one, from the rail out -- the rail is
on the band as well, keeping only its colour, which is what says which
conversation the quotation is inside. In the two windows that are real
buffers the band is as wide as the widest line of it: there is no
editor-wide ground there to match.

The pane (|nemeton-pane-window|) draws that band whether the code has
moved or not, and quotes the lines as they now are where it has not.
The floats are drawn over the file and the reader can see the line
underneath them; the pane is read beside it, and the line a comment is
about is the one thing a reader in there cannot look at without looking
away from what they are reading.

That code is read out of the checkout with `git show`, not from the
forge: the commit the note was written against is one this repository
already has. A commit that is not here -- force-pushed away -- is asked
about once and then left alone, and the thread is drawn as it always
was.

Anchoring: GitLab only takes a comment on a line the change touches.
Nemeton knows which lines those are, and says so before opening a
composer you would only have to close again.

==============================================================================
8. CONFIGURATION                                       *nemeton-configuration*

One table. `require("nemeton").setup({...})` overlays yours onto it, key
by key, and lists are replaced rather than merged. Everything below
lives in `lua/nemeton/config.lua`, which is worth reading: every value
in it says why it is what it is.

LIST                                                     *nemeton-config-list*
>
    list = {
      per_page = 30,          -- how many merge requests to ask for
      state = "opened",       -- what a queue opens on; `s` walks the four
      order = "updated_at",   -- `glab mr list --order`
      width = 0.7,            -- of the editor
      height = 0.6,
      ci = true,              -- does each row say what CI made of it
      approvals = true,       -- ...and how far its approvals have got
      drafts = true,          -- ...and what you have not sent on it
      concurrency = 6,        -- how many per-row calls at once
      stats = true,           -- does each row say how much it changes
      preview_height = 14,    -- rows of the pane under the list
    }
<
`ci`, `approvals` and `drafts` cost one API call each per row: GitLab's
merge request list carries no pipeline, no approvals, and a draft note
is yours and is in no list payload at all. The calls share one queue, a
few at a time, and each row is redrawn as its own answer lands, so the
list is readable throughout -- but on a slow forge, or a queue of
thirty, these are the switches.

`ci`, `approvals` and `stats` ask about the open rows only. What CI did
to a merge request that is merged, and who approved it before it was,
are questions for its own window on the rare occasion they are asked at
all -- and a queue of them should read as fast as it can be drawn.

`drafts` is the one worth the wait. An unsent comment lives on the forge
rather than in this editor: it is still there tomorrow, and on a machine
you are not sitting at, and this queue is the only place you would ever
be told about it.

`stats` is one GraphQL call for all the open rows, and the only GraphQL
in the plugin. REST publishes no line totals anywhere. An instance whose
GraphQL will not answer leaves the column empty by itself.

COMMENTS                                             *nemeton-config-comments*
>
    comments = {
      sign_open = "",       -- a thread still owed an answer
      sign_resolved = "",   -- one that is settled
      sign_draft = "",      -- one of yours, not sent yet
      sign_span = "▎",       -- the lines the thread being read covers
      reading_ground = 0.6,  -- ...and the band under those same lines
      virt_text = false,     -- the first line of it at end of line

      reply_indent = "  ",   -- what a reply is indented by
      reply_mark = "↳ ",     -- and what stands in that indent

      accent = "DiagnosticHint",  -- which colour it leans towards
      reply_ground = 1.7,    -- how far further off an answer stands
      head_band = true,      -- a band under the head of a note as well
      heading_accent = true, -- ...leaning towards the thread's own colour
      heading = 0.06,        -- how far it leans
      reactions = true,      -- the emoji on a note, under it
      reaction_names = {...},-- ...and which ones `+` offers

<
The three signs are Nerd Font glyphs; without one they render as a box.
"●", "○" and "✎" are the pair-and-a-half to fall back to. `rail` and
`sign_span` fall back to "│". `sign_span` is drawn only while a thread
is being read in the pane (|nemeton-reading|); `false` leaves the gutter
to the bubbles alone.

`expand` is which side of the code the pane opens on
(|nemeton-pane-window|): "right" or "bottom". A comment drawn under the
line it is about is where it belongs and pushes the code apart to say
so -- four blocks between you and the next function, a paragraph wrapped
to whatever width the window happens to be, and nowhere in it to put a
cursor, so nothing in it can be acted on. The pane leaves the code its
shape, gives the prose a width of its own, and makes the thread you are
reading one you can answer where you are sitting.

`expand_anchor` is which window that pane is a split of. "window"
splits the one the code is in, so the pane arrives beside it and the
rest of the screen keeps its layout; "editor" puts it against the edge
of the whole editor -- full height down the right, full width along the
bottom, where the quickfix window already opens. `pane_width` and
`pane_height` are where it starts, and never more than half the screen
whatever they are set to: sixty columns is most of an eighty column
terminal, and a pane that leaves nineteen columns of code is a pane you
open once. It is an ordinary window afterwards, resized like any other.

A comment is wrapped to the window it is drawn in, and to `wrap` -- 80
columns by default -- wherever the window is wider than that. The floats
have to wrap: they are drawn over the code and there is nowhere for a
long line to go. `wrap` is the other limit, for the other end of it --
prose set across the whole of a wide editor is prose the eye loses its
place in on the way back to the next line. Set it to `false` to wrap to
the window and nothing narrower.

The pane does not, unless you ask it to. `pane_wrap` is off by default:
it is a real window with a real buffer, so a line too long for it is a
line to scroll sideways to rather than a line lost -- and unwrapped, a
comment keeps the shape it was written in. That is worth more than it
sounds. A fenced block, a ruled table and the two halves of a suggestion
all mean what they mean by their columns, and none of them survive being
folded at the edge of a sixty-column pane. The other half of it is the
rail: a wrapped line comes back at column zero, outside it, so the one
part of the block that says where the thread starts and stops goes
missing from exactly the lines that needed it. `pane_wrap = true` wraps
to the pane's width and accepts both.

`head_commit` puts the commit a note was written against in its head,
after the date: eight digits, the ones GitLab itself prints. The other
half of "when" -- a review comment is about code at a moment, the date
says which afternoon and this says which push, and `git show` on it says
what the file said then. A comment on the merge request as a whole was
written against no commit and gets none.

`emoji` draws a `:name:` GitLab knows as the character it names; see
|nemeton-emoji|.

`references` draws what a comment points at rather than says --
`@somebody`, and the commit it blames -- in |hl-NemetonMention| and
|hl-NemetonCommit|, blue by default. They are the two things in a
comment that are a reference to something outside it, a person to be
asked and a commit to go and read, and both are found by scanning
rather than by reading the sentence they are in. An address is not a
mention and a word is not a sha: a name has to start where a word
starts, and seven characters count as a commit only if they are both
digits and letters -- seven of nothing but a-f is a word English
happens to have, and seven of nothing but digits is a number somebody
wrote down. Nothing is marked inside a thread that is over: a settled
conversation is dimmed whole, and a blue name in one would say there is
something there to answer.

`show_resolved` is a redraw, not a refetch: resolved threads are fetched
either way.

`short_commits` draws a link to a commit as the eight digits GitLab
itself prints: a permalink is a hundred characters whose only content is
the forty at the end of it, and a comment carrying two of them is mostly
URL. Both shapes the forge writes -- `/-/commit/<sha>` and a commit of
this merge request, `merge_requests/N/diffs?commit_id=<sha>` -- and a
markdown link keeps the words its author wrote in front of the sha. Only
how a comment is drawn: |:Nemeton edit| sends back the text its author
wrote, links and all.

`syntax` costs a treesitter parse of the suggested lines, once per block
and cached. See |nemeton-syntax|.

`ground` is 0 for the file's own background and 1 for the colour its
text is drawn in; see |hl-NemetonInline| for what is done with it, and
`false` for no band at all.

`accent` is which colour the grounds lean towards: the name of a
highlight group, whose foreground they borrow. `DiagnosticHint` because
it is the colour every scheme keeps for "here is something to know
about, and nothing is wrong", which is a review comment exactly -- and
because it is reliably the quieter half of the diagnostic palette, where
`DiagnosticInfo` is a saturated cyan in enough schemes to turn every
comment in the window blue. `"Comment"` is quieter still,
`"DiagnosticWarn"` warm, like paper in a margin.

`false` is a neutral panel instead: the page's own background raised off
itself and nothing else, so a comment is told from the code by standing
above it rather than by being a colour. `true` leans each ground towards
the colour of the thread it is under, an open thread's or a resolved
one's, which says the most and costs the most.

Whatever it is set to, a settled conversation still sinks back towards
the page: the lift is halved for it, and the rail and the tick say what
state a thread is in outright.

`reply_ground` is how far the ground under an *answer* stands off, as a
multiple of `ground`. Above 1 and a reply is a step further off the page
than the note it answers; 1 leaves it flush, where the indent and the
arrow are the whole of what says so -- and both of those are two
characters at the head of a line, which is where the eye is not when it
has just finished the line above. See |hl-NemetonReply|.

`head_band` puts the head of each note on a band as well. Backgrounds
are the one signal in these windows that cannot be stacked -- a thread
with an answer and a suggestion in it already carries the block's
ground, the answer's, the code the thread was written against and both
halves of the diff -- so this one earns its place by being the quietest
of them: `heading` is a sixteenth of the way into a colour, which is a
heading you find without reading and not a bar across the note. `false`
where the block's ground and the author's own colour are enough.

`heading_accent` is which colour that band leans towards, which need not
be -- and by default is not -- the one the ground under it leans
towards. `true`: the colour of the thread the head belongs to, an open
thread's or a resolved one's. It is the one place in the block where
saying so is nearly free, because the head is one line of the several a
note takes and it is the line naming who is talking, which is the line
you are on when you want to know whether the argument is over. The
ground under it stays the calmer colour the whole conversation is on.

The other two answers are `accent`'s: `false` for no lean, where
lightness alone tells the head from the body -- and lightness is the one
direction that costs whatever is written on the band -- or the name of a
group to borrow from.

`heading` is how far it leans, on the same scale, and is small for what
it leans into: a diagnostic colour is a colour chosen to be seen from
across the room. See |hl-NemetonHead|.

COMPOSER                                              *nemeton-config-compose*
>
    compose = {
      height = 10,            -- rows of the split you write in
      mentions = true,        -- complete `@name` from the project
      mention_menu = true,    -- ...and put the menu up as you type
      emoji = true,           -- complete `:name:` from the shortcodes
      emoji_menu = true,      -- ...and put that menu up as you type
      remember = true,        -- keep what was closed unsent
      remember_days = 30,     -- ...for this long
      remember_path = nil,    -- ...here; nil is beside the log
    }
<
`mentions` puts the people on this project -- the members of it and of
the groups above it, which is who GitLab notifies -- on `<C-x><C-o>` in
the composer. They are fetched when the window opens, once per
repository per editor session, because completion is synchronous and a
round trip inside a keystroke is a freeze. A forge that will not answer
leaves the key completing nothing and says nothing about it.

`emoji` and `emoji_menu` are the same two switches for the `:name:` of
an emoji (|nemeton-emoji|), on the same key: one `omnifunc` answers for
both, because there is one `omnifunc`. An engine reads
`require("nemeton.emoji").candidates(prefix)`.

`mention_menu` puts the menu up as the `@` is typed. It needs a Neovim
that can hold `completeopt` for one buffer (0.11 and newer): a menu that
picks the first name for you is worse than no menu, and this plugin will
not set a global option to avoid that. On an older Neovim the key still
completes. Using a completion engine instead? Point it at
`require("nemeton.mentions").candidates(root, prefix)`, which is what
the omnifunc reads.

GLAB                                                     *nemeton-config-glab*
>
    glab = {
      bin = "glab",
      timeout = 30,             -- seconds before a call is hung

      host = nil,               -- string | fun(): string | nil
      token = nil,              -- string | fun(): string | nil
      prompt_for_token = true,
    }
<

                                                             *nemeton-tracking*
`track` is about what `glab mr checkout` leaves behind. It points the
branch at the merge request:
>
    branch.<name>.remote = origin
    branch.<name>.merge  = refs/merge-requests/<iid>/head
<
so that `git pull` follows the merge request. Nothing on this side has a
remote-tracking branch then -- `refs/merge-requests/*` is not in any
remote's fetch refspec -- so git answers "no upstream" to every question
about being ahead or behind, and so does everything else reading the
repository: a statusline, or lazygit, which draws a branch configured
with a remote it cannot count against as a purple `?`.

For a merge request from this project the two are the same commits under
two names, so nemeton puts the ordinary upstream back after the
checkout: one `git fetch <remote> <branch>`, one `git branch
--set-upstream-to`. Both are quiet, both are allowed to fail, and both
are in the log. |nemeton-log|

What glab writes as `branch.<name>.remote` is as often the remote's URL
as its name, and neither git command above takes a URL. So it is turned
back into a name first -- the remote whose URL it is, compared with a
`.git`, a trailing slash and any `user@` taken off both sides. A value
belonging to no remote of this repository is left alone rather than
guessed at.

Never for a merge request from a fork -- its source branch is not on
this remote, and a branch of the same name that happens to be is a
different branch entirely -- and never for a checkout under a branch
name of your own, which is not a branch this configured. `track =
false` leaves what glab wrote alone.

9. CREDENTIALS                                           *nemeton-credentials*

`host` and `token` are exported to every `glab` call as `GITLAB_HOST`
and `GITLAB_TOKEN`. Both default to `nil`, which is usually right: glab
infers the host from the repository's git remote, and `glab auth login`
keeps a token in the system keyring.

                                                         *nemeton-config-host*
`host` -- a string, or a function returning one. Set it only for a
self-managed instance glab cannot infer. One sharp edge, and it is
glab's: with `GITLAB_HOST` set, glab refuses to work in a repository
whose remotes point elsewhere ("none of the git remotes configured for
this repository correspond to the GITLAB_HOST environment variable"). If
you review across two instances, leave it nil.

                                                        *nemeton-config-token*
`token` -- a string, or a function returning one. A function is the
point: it is called once per editor session and cached, so it is where
you shell out to a password manager rather than putting a `glpat-...` in
a dotfile that ends up in a backup, a screen share, and eventually a
repository.
>
    token = function()
      return vim.trim(vim.fn.system("pass show gitlab/token"))
    end
<
                                                       *nemeton-config-prompt*
`prompt_for_token` (default `true`) -- when glab answers 401, or when
there is no token anywhere, nemeton asks for one with |inputsecret()|
(masked, and not in `:history`), keeps it in memory for this Neovim
session only, and retries the call that failed. Several calls failing at
once share one prompt. Set it to `false` to have calls simply fail.

NOTHING PERSISTS A TOKEN. A prompted token lives in a Lua local for as
long as the editor does: not written to your config, not to disk, not
handed to `glab auth login`. `:Nemeton forget-token` drops it.

A 403 never prompts. That is a token that works and an account that may
not touch the project, and asking for a different token at a permission
error trains exactly the wrong reflex.

10. HIGHLIGHT GROUPS                                      *nemeton-highlights*

Every colour is a `Nemeton*` group linked to one your colourscheme
already defines, so all of them are one `:highlight` away. They are set
with `default`, and re-linked on every |ColorScheme|.

    NemetonSignOpen       a thread still owed an answer   DiagnosticInfo
    NemetonSignResolved   one that is settled             Comment
    NemetonDraft          one of yours, not sent yet      DiagnosticWarn
    NemetonAuthor         who said it                     Title
    NemetonBranch         a git ref                       Directory
    NemetonMention        somebody a comment calls on     DiagnosticInfo
    NemetonCommit         a commit a comment points at    DiagnosticInfo
    NemetonLink           a page a comment points at      DiagnosticInfo,
                                                          underlined
    NemetonHeading        a heading inside a comment      Title
    NemetonHeading1..6    which level of one it is        Title, by weight
    NemetonBold           a word written `**like this**`  bold, no colour
    NemetonItalic         one written `*like this*`       italic, no colour
    NemetonStrike         one written `~~like this~~`     struck through
    NemetonCode           one written `` `like this` ``   String
    NemetonThread         what they said                  Normal's fg
    NemetonMeta           when, where, how many           Comment
    NemetonResolved       the tick on a settled thread    DiagnosticOk
    NemetonOk             passed, approved, enough        DiagnosticOk
    NemetonBad            failed                          DiagnosticError
    NemetonBusy           running, pending, not yet       DiagnosticWarn
    NemetonAdded          a line the change adds          Added
    NemetonRemoved        one it takes away               Removed
    NemetonHint           the key hints across a window   Comment
    NemetonKey            the key itself, inside a hint   Special

                                                          *hl-NemetonMention*
                                                           *hl-NemetonCommit*
                                                             *hl-NemetonLink*
`NemetonMention`, `NemetonCommit` and `NemetonLink` are what a comment
points at rather than says, and what |nemeton-follow| goes to. All three
are `DiagnosticInfo`, since all three are one kind of thing: a reference
out of the comment. Three groups rather than one so that any of them can
be moved on its own.

`NemetonLink` carries an underline on top of that colour, because that
is what a link has looked like since before any of this: its words are
the author's own sentence, and the line under them is what says they are
also a door. It is copied from `DiagnosticInfo` rather than linked to
it, because a `:highlight link` is all or nothing and leaves nowhere to
hang the underline -- so a scheme that moves `DiagnosticInfo` moves this
with it only on the next |ColorScheme|, which is when this plugin reads
its colours anyway. |nemeton-config-comments|

                                                          *hl-NemetonHeading*
`NemetonHeading` is a heading inside a comment, drawn without the hashes
that made it one. `Title` -- the colour a name is drawn in here -- since
a terminal has no larger type to say it with.

`NemetonHeading1` to `NemetonHeading6` are which level of one, which the
hashes used to say and nothing else on the line does. A terminal cannot
draw a bigger word, so the six are told apart the way everything else in
these windows is: loud at the top and quiet at the bottom. Underlined
and bold is a title with a rule under it, bold is a section, plain is
the colour alone, and the three below that are the same fall in
|hl-NemetonMeta|'s colour -- which is where a heading nested that deep
in a review comment belongs. The colours are copied from
`NemetonHeading` and `NemetonMeta` on every |ColorScheme|, for the
reason |hl-NemetonLink| is copied: a `:highlight link` is all or nothing
and leaves nowhere to hang the weight.

                                                             *hl-NemetonBold*
                                                           *hl-NemetonItalic*
                                                           *hl-NemetonStrike*
                                                             *hl-NemetonCode*
`NemetonBold`, `NemetonItalic` and `NemetonStrike` are the weight a word
was written with. They carry no colour and none is wanted: extmarks
compose, so what these do is put a weight on whatever colour the word
was already drawn in -- dim inside a settled thread, blue and underlined
inside a link, the language's own inside a suggestion.

`NemetonCode` is a code span, which is a colour and not a weight: it is
the one piece of a comment that quotes something rather than says it,
and `String` is the colour an editor already draws quoted text in.
|nemeton-config-comments|

                                                               *hl-NemetonWas*
`NemetonWas` is the band the code a thread was written against is drawn
on when that is not what the line says any more |nemeton-drift|. Not a
link: it is your own background moved towards the colour a line taken
away is drawn in, which is what that code is, with the text left the
colour text is -- the background is carrying the verdict, and red words
on a red band are a line you have to work at to read. Without
'termguicolors' there is nothing to mix and it is |hl-NemetonRemoved|,
as it used to be.

                                                         *hl-NemetonReading*
`NemetonReading` is the band under the lines of code the conversation
in the pane is about |nemeton-reading|. The same ground the
conversation itself is drawn on -- the two are one block read in two
windows -- at `comments.reading_ground` of its strength, because this
one is under code that is being read rather than under prose.

                                                        *hl-NemetonReaction*
                                                    *hl-NemetonReactionMine*
`NemetonReaction` is the count beside a reaction, and
`NemetonReactionMine` the count beside one of your own. Only the count:
an emoji is drawn from the font's own palette whatever a highlight
says, so the one thing left to colour is the number -- and the one
thing worth saying with it is which of the rows you are already in,
since `+` on one of yours takes it back.

                                                           *hl-NemetonReply*
                                                    *hl-NemetonReplySettled*
`NemetonReply` is the ground under an answer, and `NemetonReplySettled`
the same inside a thread that is over: the ground its thread is on,
standing `config.comments.reply_ground` times as far off the page. A
conversation is then a block with steps in it, and which note you are
reading is a thing you see rather than a thing you count indents to
work out.

It starts after the rail, which stays on the thread's own ground the
height of the thread: the rail is what says these notes are one
argument, and an answer drawn over it is a stripe across the block
rather than a panel inside it.

                                                            *hl-NemetonHead*
                                                    *hl-NemetonHeadSettled*
`NemetonHead` is the band the head of a note is drawn on -- who said it
and when -- and `NemetonHeadSettled` is the same for a thread that is
over; `NemetonHeadReply` and `NemetonHeadReplySettled` are the pair for
the head of an answer, which sits on the answer's ground. None of the
four is drawn unless `config.comments.head_band` asks for it.

Each is the ground its block is on |hl-NemetonInline|, taken
`config.comments.heading` of the way into
`config.comments.heading_accent` and then put back at the lightness it
started from, plus a hair.

Its own colour, and not the one the ground under it leans towards: a
heading told apart by lightness alone is a brighter band, and brighter
is the one direction that costs what is written on it -- the date, in
the comment colour, which is the quietest group here. A tint of its own
makes the head a different colour without making it a lighter one, and
leaves the body the page's own.

Not far, either way. Every colour on offer is somebody's diagnostic
colour, and a head that has gone most of the way into one is a bar
across every note rather than a shade of the conversation it belongs to.

Told apart by colour and not by being lighter, which is the point:
lighter is nearer the colour of the text, and what is written on this
band is the quietest group in the plugin -- the date, in the comment
colour. A heading is a different colour, not a brighter one.

A note is two things read two ways: a line of bookkeeping that is
skimmed, and a thing somebody said that is read. They were told apart by
colour alone -- a name in the title colour, a date in the comment
colour, and then the words -- and in a thread with four answers in it
that is four places the eye has to find by reading. In the comments
window |nemeton-notes-window| the band does a second job: it says where
one entry ends and the next begins, which the blank line between them
says quietly.

                                                     *hl-NemetonSuggestNew*
                                                     *hl-NemetonSuggestOld*
`NemetonSuggestNew` and `NemetonSuggestOld` are the two bands a
suggestion is drawn on: the lines it would put there, and the lines it
would take away. Your own background moved towards the colour each half
used to be drawn in -- less far than |hl-NemetonWas|, which is beside
them in the same block and is a quotation rather than half of a diff --
and each keeps that colour as its foreground, for what is on the band
and is not code: the `+`, the `-`, and every line of a language nothing
here can parse.

A band and not only coloured text, because the text is no longer free to
carry it: the code inside a suggestion is drawn in the colours of its
own language |nemeton-syntax|, and a keyword is the colour a keyword is
on both halves of the diff. A background is the one part of a line that
syntax highlighting does not use. Without 'termguicolors' there is
nothing to mix, both fall back to |hl-NemetonAdded| and
|hl-NemetonRemoved| as text, and the line stays on the conversation's
own ground.

                                                            *hl-NemetonInline*
                                                     *hl-NemetonSettled*
`NemetonInline` is the ground a conversation is drawn on: your own
background lifted towards the colour your text is drawn in -- lighter in
a dark colourscheme, darker in a light one. A panel raised off the page,
and by default no more than that; `config.comments.accent` tints it
towards a colour as well.

Under the code where the conversations are expanded, and inside the
three windows that draw one -- |:Nemeton notes|, |:Nemeton conversation|
and the peek float. There a block on a ground of its own is what makes a
comment look like one: without it four notes in a row are words on the
same background as everything else in the window, and where one ends and
the next begins has to be read to be found. The ground runs to the
right-hand edge of the window, and the line between two of them does
not, so each is a box with edges.

Those three windows take the editor's own background rather than
`NormalFloat`, because this band and every band inside it -- the head of
a note, quoted code, the two halves of a suggestion -- are mixed out of
`Normal`. Drawn on a float's background instead, how far the block
stands off the page would be whatever the colourscheme happened to make
the difference between the two rather than `comments.ground`.

How far it stands off the page is `config.comments.ground`, and the
whole of it: the tint decides which way the band leans and is then put
back at the lightness the lift asked for. Anything else and the tint is
a second lift nobody agreed to -- the colour of an open thread is a
bright one, and a seventh of it mixed into a dark background was half as
much again. Everything in the comment colour is read against this band.

It is set far enough to hold its own against whatever else paints these
lines: a diff plugin's red and green sit on the code above and below,
and a ground a whisper away from the file's own reads as one more band
of that. `false` for no band, where the rail and the dimmed text carry
it alone.

`NemetonSettled` is the ground under a conversation that is resolved:
half as far off the page, and towards the resolved colour instead where
there is an accent to lean towards at all. Whether a thread is
still owed an answer is the thing you want to know before reading a word
of it, and a block has a colour before it has anything else -- so an
argument still going on stands off the page, and one that is over sinks
back towards it.
>
    :hi NemetonInline guibg=#20242c     " pick another
    :hi link NemetonInline Normal       " take it away
<
The colours drawn on either ground -- `NemetonInlineAuthor`,
`NemetonSettledAuthor` and the rest -- are derived from it when it is
set, so nothing in the block carries a background of its own through the
middle of it. Setting the ground is enough; the derived groups follow.

Without 'termguicolors' there is nothing to mix -- sixteen colours have
no "a seventh of the way" towards anything -- and both fall back to
|hl-CursorLine|,
where the tick and the dimmed text carry it alone.

11. HEALTH                                                    *nemeton-health*

`:checkhealth nemeton` -- and it asks the forge rather than assuming:

  - Neovim's version against the floor;
  - `git`, and whether you are in a repository;
  - `glab`, its version, and whether it is authenticated;
  - which host and which token source are in effect (never the token
    itself, and never printed into a buffer you are about to paste into
    an issue);
  - the GitLab version, against the 15.10 that draft notes need;
  - whether the GraphQL endpoint answers, which is what the size column
    in the list needs;
  - where the log is being written.

12. THE LOG                                                      *nemeton-log*

Every subprocess nemeton runs -- every `glab` call, so every API call,
and the two `git rev-parse`s -- is written to
>
    ~/.local/state/nemeton/nemeton.log     ($XDG_STATE_HOME if you set it)
<
two lines per command, one when it starts and one when it ends:
>
    2026-08-30T14:27:13.747 [4] run  glab api ... env=GITLAB_TOKEN=<set>
    2026-08-30T14:27:13.752 [4] exit 0  5ms
<
Both ends, because the call worth reading about afterwards is often the
one that never came back. The number in brackets pairs them up: several
requests are in flight at once and their lines interleave.

The token is not in there. The environment is logged by name and by
presence -- `GITLAB_TOKEN=<set>` -- because whether a token was exported
is the question the log has to answer and which one it was is the
question it must not. Arguments and the first line of a failure's stderr
are scrubbed on the way in. What you write in a comment does not go in
either: a POST is logged as `stdin=301B`.

One rotation, at `log.max_bytes`: past it the file becomes
`nemeton.log.old` and a fresh one starts, so two files bound the disk.

13. LIMITATIONS                                          *nemeton-limitations*

  - GitHub. `lua/nemeton/glab.lua` is the seam -- the same handful of
    operations, a different binary -- but GitHub's review model is not
    GitLab's, and pretending otherwise in the data model would cost
    more than waiting.
  - The diff. You review the branch as it stands, in ordinary
    buffers. Seeing the change itself is another plugin's job.
  - Threads on the old side. Fetched and indexed with `side = "old"`,
    but there is no old side on the screen to draw them against, so
    they are drawn on the new line number.
  - Line drift. If somebody pushes while you are reviewing, the local
    HEAD stops being the revision the threads were written against.
    Nemeton says so once, on checkout, and otherwise draws the threads
    where they claim to be.
  - Resolving an overall thread. GitLab only makes diff notes
    resolvable in practice, so resolving lives on the gutter.
  - Pagination in the list. The first `list.per_page`, ordered by
    what was touched last.
